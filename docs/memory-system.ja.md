# 記憶・履歴システム解析

## 1. 「記憶」と呼べるものの分類

このプロジェクトには単一の長期記憶モジュールはありません。役割の異なる保存層を組み合わせています。

| 層 | 保存場所 | 寿命 | LLMへ再投入 |
| --- | --- | --- | --- |
| ブラウザ履歴 | JavaScriptの `history` | 画面を閉じるまで | 毎ターン |
| セッション保存 | `profiles/latest_session.json` | 明示保存後 | 読込後に再投入 |
| 圧縮履歴 | リクエスト内で一時生成 | 1回のLLM呼び出し | する |
| 会話監査ログ | `logs/chat.jsonl` | ファイル削除まで | 通常はしない |
| キャラクター人格 | `Character/*/profile.txt` | 永続 | system messageへ投入 |
| Webメモ | フロント状態と今回のリクエスト | 自動会話中など | user messageとして投入 |

## 2. ブラウザ履歴

ブラウザは次の単純な配列を持ちます。

```json
[
  {"role":"user","content":"..."},
  {"role":"assistant","content":"リノン: ..."}
]
```

2Pの話者名は `assistant` roleとは別のフィールドにせず、本文の接頭辞として保存します。この履歴が通常会話の短期記憶です。

「コンテキストを消去」すると、履歴、音声キュー、Webメモ、表示メッセージをまとめて初期化します。

## 3. セッション保存

`/api/session` は次を `profiles/latest_session.json` へ保存します。

- キャラクター選択
- system promptとTTS Caption
- 参照音声
- モデルとコンテキスト上限
- 話速と返答長
- 1P/2P設定
- 感情設定
- Web検索設定
- 会話履歴

読み込み時にはroleが `user` または `assistant` で、本文が空でない履歴だけを復元します。

これは「会話の続きを再開するためのスナップショット」であり、事実単位の記憶ではありません。

## 4. コンテキスト圧縮

履歴が長くなると、古い発言は次のようなテキストへ変換されます。

```text
以下は古い会話の要約です。
過去のお題: ...
古い会話の圧縮ログ:
ユーザー: ...
リノン: ...
```

この圧縮文を `user` roleで先頭に置き、その後へ直近の会話を続けます。

### なぜsystem roleではないか

コード上の明示的理由はありません。推測として、人格system messageを汚さず、古い会話を参考資料として扱わせるためと考えられます。

### 失われる情報

- 古い会話の厳密な順番
- 長文の中央・末尾以外
- 誰が何を約束したかという構造
- 感情の時系列
- キャラごとの関係性変化

## 5. 会話ログ

`logs/chat.jsonl` は1ターン1JSONで追記されます。

主な記録:

- 時刻
- ユーザー入力と返答
- 話者
- 使用モデル
- 返答長・話速
- emojiStyleと表情
- Web検索結果
- TTS Captionと参照音声
- 文分割結果
- 各wavのURLと生成時間
- コンテキスト圧縮統計

このログはLLMの記憶として自動利用されません。研究用の観測・再現・集計データに近い位置付けです。

`/api/log-summary` は表情と絵文字の使用回数、直近ログを集計できます。

## 6. キャラクター人格という長期記憶

`systemPrompt` はキャラクターの恒常的な性格、嗜好、禁止事項、会話例を保存します。毎ターンsystem messageへ入るため、最も強い永続記憶です。

ただし会話から自動更新されません。作者またはユーザーが明示的に編集する静的記憶です。

## 7. Webメモ

Web検索結果は、会話から抽出した検索語と最大3件の結果を短く加工してLLMへ渡します。

自動会話では検索結果をフロントの `autoWebContext` に保持し、新しいお題で再検索するまで再利用できます。

これは外部知識の一時キャッシュであり、セッションの恒久的な意味記憶には統合されません。

## 8. 現在ないもの

次の仕組みは実装されていません。

- ベクトルDB検索
- 会話からの人物・嗜好・出来事抽出
- 記憶の重要度評価
- 忘却・減衰
- キャラクターごとのエピソード記憶
- 記憶同士の矛盾解決
- ログから関連記憶だけを検索するRAG

## 9. 細かな実装テクニック

### JSONL

会話ログはJSON配列ではなくJSONLなので、全ファイルを書き直さず1行追記できます。途中で一部が壊れても、正常な行だけ読めます。

### コンテキスト統計

`full`, `sent`, `limit`, `effectiveLimit`, `compacted`, `recentMessages` を返すため、UIやログから圧縮の発生を追跡できます。

### 保存と実行の分離

セッション保存は明示操作です。通常会話のたびに `latest_session.json` を更新しないため、書き込み量を抑えますが、保存前に終了すると履歴は復元できません。会話内容自体はJSONLログには残ります。

## 10. 研究用途での発展方向

この構造へ長期記憶を追加するなら、既存の `history` を直接肥大化させず、別の記憶層を追加するのが適しています。

例:

1. 会話終了時に事実候補を抽出する。
2. `subject`, `predicate`, `object`, `confidence`, `sourceTurn` として保存する。
3. 次の入力との関連度で数件だけ検索する。
4. system promptではなく「参考記憶」として別messageに注入する。
5. キャラクターが知り得る情報かどうかを話者別に管理する。

現在の規則ベース圧縮は残し、エピソード記憶を補助層として加えると比較実験しやすい構成です。
